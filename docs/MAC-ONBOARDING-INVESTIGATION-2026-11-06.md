### Procedure for subsequent separately authorized work

1. **Preserve the failure before changing it.** Keep original samples, failed assertions and negative controls. Classify observed symptoms as busy-main, waiting-main, memory growth or responsive-but-broken UI. A heartbeat, framework stack frame, low CPU sample or reviewer opinion alone cannot establish correct action completion or a proven root cause. Make one falsifiable hypothesis and controlled change, reproduce with matched inputs, revert disproven experiments and remove temporary switches before shipping.
2. **Separate monitoring from collection and repair.** Any future monitor must run outside the main actor it observes, keep at most one pending acknowledgement, use monotonic timing and generation-safe recovery, and explicitly handle stop/cancel and debugger/sleep/suspension. Use bounded sanitized action breadcrumbs and signposted application intervals, not raw payloads or per-render preferences writes. A developer-side collector must validate PID, path, binary/build and matching symbols, survive denied/unavailable/timed-out collection, and never restart or kill an attached owner process. Monitoring is not automatic repair.
3. **Use the canonical execution gates in order.** Stage shared diagnostic contracts and deterministic injected-clock/collector tests first. Then, only with separate authorization, run bounded busy/waiting/responsive-but-broken fixtures and healthy controls. Extend the existing PID-scoped native harness for actual onboarding, empty/populated Overview, editable tuning routes, reselection, sheet/settings/scroll/resize and window/menu-bar transitions. Add all needs injected discovery success, partial failure, retry and cancel with persistence and interactive Overview assertions, not a real subnet scan or only decision-helper tests.
4. **Keep bounds and privacy explicit.** The canonical document's timing, capture-size, count, cooldown and retention values are proposed candidates, not accepted platform standards or measured budgets. Declare budgets before paired baseline/instrumented optimized-build measurements, record sample counts and memory definitions, and bound soak duration, queues and storage. Keep sanitizer-heavy runs separate. Use allowlisted local evidence, adversarial export-redaction checks and explicit unknown/unavailable outcomes. No analytics dependency, automatic cloud/model upload, privileged collector or weakened signing/sandboxing is authorized. Retention is limited to diagnostic-owned storage without following symlinks or deleting owner files.
5. **Assert scope, not just demo mode.** Preserve canonical single-app installation and owner state, isolated preferences and injected transports. Demo mode alone does not prove public HTTPS is disabled. Future workflow evidence must include a request journal demonstrating zero device-control requests and zero unauthorized real destinations. Disclose any separately launched fixture first, validate its identity and stop cleanup at its owned PID boundary. The existing phone, scanner and hardware holds still apply.
6. **Require complete receipts and a final verifier.** Each FD gate needs status, named checks and actual nonzero execution counts, source commit plus dirty-tree manifest, binary identity, UTC timing, exact commands/arguments, environment, assertions, evidence paths and limitations. A timeout is a failed scenario, never permission for unbounded retry or an ambiguous repeated action. Preserve failed attempts, report skips explicitly and run the final affected integration/acceptance verifier after the last implementation edit. A compile, empty filter, screenshot-existence check or this methodology review cannot pass a workflow gate.
